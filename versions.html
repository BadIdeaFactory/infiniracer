★ brake-to-drift around corners ★
▶ PLAY V017

PROMPT

CHANGES

  • New car.slipAngle field — radians offset between the car's heading and its actual motion direction. Translate now uses motionDir = heading + slipAngle instead of plain heading, so the world scrolls diagonally during a slide
  • Drift trigger: brake held + steer commitment over DRIFT_STEER_MIN = 0.18 + speed over DRIFT_MIN_SPEED = 220. Below the threshold the brake is just a brake (no slide)
  • Yaw boost while drifting (DRIFT_YAW_BOOST = 1.55) — heading rotates faster than motion. Slip angle eases toward ±DRIFT_MAX_SLIP = 0.50 rad (~29°) opposite the steer at 1/τ = 5.5. When the trigger releases, slip decays back to zero at 1/τ = 6.5 — grip recovers
  • Speed dynamics: brake during drift is softened (DRIFT_BRAKE_MUL = 0.30) so the slide actually continues, plus DRIFT_DRAG = 90 u/s² of bleed so it isn't free speed
  • Visual cue: wheels brighten to hot orange (#ff8d3a) and thicken (1.4 → 1.8 px) while |slipAngle| > 0.06 rad. The diagonal world-scroll already shows the slide; the brighter wheels just emphasise it
  • commitReset() clears slipAngle alongside the rest of the car state

V011
★ webgpu opt-in ★
▶ PLAY V011 (WebGPU)

PROMPT

I still feel like if we use webgpu we'd free ourselves up to worry less about performance, we can always rollback if it doesn't work

CHANGES

  • Optional WebGPU renderer for beams + dots. Activated by ?renderer=webgpu in the URL; falls back automatically to canvas 2D if navigator.gpu is missing or device init fails. Game logic, joystick, crash explosion, and HUD stay on the canvas-2D layer
  • Two-canvas stack: <canvas id="game-gpu"> at z-index 0 (WebGPU output, opaque, full screen) sits behind the existing <canvas id="game"> at z-index 1 (canvas-2D, cleared transparent when GPU is active so the layer below shows through)
  • Line shader (WGSL): one instance per beam, vertex shader expands a quad along the line with rounded-cap glow padding, fragment shader computes capsule SDF and outputs color × (crisp + exp-falloff glow) with additive blend. Single draw call replaces the 2-pass canvas-2D stroke loop
  • Dot shader (WGSL): billboarded quad per dot, fragment evaluates halo + mid + hot-core layers from one radial SDF in a single draw call. Replaces the 3-fill-per-dot canvas-2D loop
  • Hex-color → RGBA float cache so per-frame instance buffer marshalling is one Map lookup per beam/dot
  • Per-frame instance buffers grow on demand (start 256 lines / 512 dots, double when needed) and are reused across frames
  • device.lost handler clears the webgpu reference so we automatically fall back to canvas 2D if the GPU disappears mid-session
  • Canvas-2D crisp beam pass deduplicated (an earlier edit had accidentally left a duplicate copy)

OPENING NOTES

  • To opt in: append ?renderer=webgpu to the URL (the PLAY button on this card already does)
  • Without the flag, the game runs the same canvas-2D path as v010
  • If your browser doesn't support WebGPU (Firefox < 141, Safari < 26, Chromium without GPU), it logs a warning and silently falls back

SHADER CRISPNESS FIX

  • First pass used exponential glow falloff (exp(-d * k)) which bled softer than canvas-2D's hard-edged 2-pass stroke. Switched both shaders to smoothstep with hard edges matching the canvas-2D layers exactly: line crisp inner (α 1) + mid-glow ring (α 0.26) at width × 2.6; dot halo + mid + white core as three hard-edged disks. Smoothstep starts at the disk/line edge so the interior keeps full intensity (no AA softening of thin lines)
  • Performance honesty note: at 60 fps cap on a fast Mac, both renderers easily hit vsync — the WebGPU win is headroom, only visible if scene density grows past what canvas-2D can sustain. If that headroom isn't currently valuable, this version can be ignored and v010 remains the active baseline

★ perf + leak fix ★
▶ PLAY V010

PROMPT

there seems to be a few performance issues, especially in Firefox, please look into improving performance, maybe we can use webgpu related stuff. also with firefox I left ot on overnight and it slowed to a crawl. memory leak?

CHANGES

  • Memory leak fix: trimWorld() splices old track[] segments + deletes far-behind sceneryChunks entries every ~1s; lastSegIdx is adjusted so the window math stays valid
  • Intersection scan capped at 6000 pair checks per frame so heavy scenery can't make it dominate
  • Vignette gradient cached and rebuilt only on resize (was being recreated every frame)

  • FPS readout added to the HUD for quick A/B perception checks without DevTools
  • WebGPU not used — bottlenecks were JS-side state churn + unbounded arrays; canvas 2D handles this scene fine if we don't fight the rasterizer
  • Hotfix: moved _vignette declaration to the top of the IIFE — initial resize() ran before let _vignette, throwing TDZ ReferenceError on load
  • Reverted: the path-batched beam + dot renderers I shipped first turned out to be slower in both browsers (worse in Firefox). Building one big path with hundreds of arc/line subpaths and filling it under "lighter" hits the complex-path slow path; the state-change savings don't pay back. Back to per-element draws for now
  • The actual win — Firefox profile pinpointed it: drawScanlines was eating 67% of frame time (full-screen fillRect with globalCompositeOperation = "overlay"), and the per-frame radial-gradient vignette another 14%. 81% of CPU on two effects that don't need to be in JS at all. Both moved to body::before / body::after CSS pseudo-elements layered over the canvas — the browser compositor handles them effectively for free. Visual result identical
  • Follow-up profile (21× fewer total samples) revealed two smaller spikes — both addressed:
    • Joystick labels: re-issuing ctx.font + 3× fillText every frame triggered Style computation. Pre-baked to three offscreen canvases at updateStickGeom; render now does drawImage
    • updateHUD: was setting textContent on 4 spans + running toLocaleString + writing to localStorage every frame the score climbed. Now diffed against last-displayed values — DOM only updates on actual change. Best-score writes debounced via setInterval(saveBestScore, 3000) + pagehide save
    • carTrackInfo() result cached per frame so render() and updateHUD() share one nearest-segment search
  • Follow-ups (third profile pass):
    • Beam glow reduced to 2 passes. Dropped the wide × 5 / α 0.10 outer-glow pass — widest line caps to rasterize, contributed least to bloom. Mid pass slightly bumped (× 2.4 α 0.22 → × 2.6 α 0.26) so the visual stays close. Kept
    • Joystick labels bake made dpr-aware (was rendering at 1× and being upscaled on retina displays). Kept
    • Tried + reverted: baked the joystick's static rings / ticks / glows into two offscreen canvases (one source-over, one composited "lighter") so each frame would be 2 drawImage calls. Profile showed it was slower in Firefox — drawJoystick went 5.2% → 8.4%, and drawImage appeared as a brand-new 7.9% entry. Likely cause: the bake bbox is mostly transparent space but Firefox's "lighter"-blend canvas-to-canvas drawImage still pays per-pixel work over the full ~350×350 region, while the original live draws only paid for actually-stroked pixels. Reverted to the previous live drawJoystick. Cardinal ticks now use a single 4-subpath stroked path (one stroke call instead of four) — small consolation
